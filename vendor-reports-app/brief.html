Vendor Reports

A weekly progress email to every dealership, generated from a fixed template and sent automatically — so nobody has to call for a status update, and nobody has to write one.

A monday-code hosted app — Node backend, React frontend — surfaced in the workspace as a Custom Object, the same deployment shape as the QBO job sync project. A monday-code cron job fires every Friday, builds each vendor's report from column values, renders it through a fixed HTML template, and emails it.

Nothing is generated and nothing is read from Updates or notes. Every line traces to a column on Vendors, Jobs or Tasks. Same board state in, byte-identical email out. No AI, no credits.

Architecture

Five moving parts

Trigger

monday-code scheduler — native cron, UTC, 5 jobs per region. Hits /mndy-cronjob/weekly-reports.

Read

monday GraphQL — Vendors, Jobs, Tasks. Columns only.

Build

Pure function. Board state → report object. No network, no model, fully testable.

Send

Transactional email API over monday-code's static outbound IPs.

Record

monday-code Storage — history and idempotency keys. No Updates written.

The Custom Object app feature renders full-screen from the left pane, independent of any board — the standalone feel you're after. A board view would trap it inside Vendors; a dashboard widget is too small.

The cron scheduler is the piece that matters most: it means the send is genuinely unattended. The app does not need to be open, and nobody has to remember Friday.

Email goes out through a transactional provider rather than monday's own email, which caps at 256 KB and turns File-column attachments into links external recipients can't open. Outbound traffic from monday-code leaves on a static IP range, so the provider can allowlist it.

Template rules

Every line is a lookup, not a judgement

The whole report is four rules. Anything that can't be resolved by one of them doesn't appear.

1 · The progress bar

Each Job carries up to 16 optional phases, each with a …? column saying whether it applies to this home. That's the denominator. Phases whose task reads Done or Invoiced are the numerator.

A home that needs no septic isn't penalised for not having one — which is what makes the bar honest, and it's a number nothing in monday shows today. Note that Invoiced must count as complete: it's a billing state, not a work state, and 83 tasks sit there right now.

2 · Completed this week

Any in-scope task whose Finished Date falls inside Mon–Sun of the week just ending. Rendered as {Task name} — {Day, Mon D}. If empty, one fixed line replaces the section: "No tasks were completed on this home this week."

3 · Still to do

Every in-scope phase not yet complete — including phases with no task created yet, which render from the phase name. Each gets exactly one suffix, first match wins:

ConditionRenders as
Task status is Working on itIn progress
Task status is WaitingOn hold
Schedule start date is setScheduled {Day, Mon D}
none of the aboveNot yet scheduled

Sorted soonest-scheduled first, then unscheduled, then build order. If empty: "All scheduled work on this home is complete."

4 · What never appears

No crew names. No subcontractor names. No prices. No task IDs. No content from Updates or notes — those stay internal. No sentence assembled by a model. The only free text that can reach a vendor is a job name, an address, and a task name, all typed by the office and already visible on the board.

A useful consequence: the builder is a pure function, so it can be golden-file tested — fixed board fixture in, byte-identical HTML out. Report bugs become regressions you catch in CI rather than things a customer notices.

Readiness

What has to be fixed first

Measured against live account data today. The first three decide whether the reports are trustworthy or actively misleading.

80

of 141 jobs have no Bill to vendor. They'd appear in no report at all.

6

of the 17 active vendors have no email — including Titan Midland (14 jobs) and Palm Harbor (7).

4×

Solitaire exists under four spellings, Palm Harbor three, Titan two.

112

of 576 tasks have a Schedule set — so most "Still to do" lines start out unscheduled.

24

of 576 tasks have photos. Not enough to build on — out of scope for v1.

A vendor receiving a report that omits half their homes is worse than receiving nothing — it reads as "you lost my house." So the cron job refuses to send to any vendor failing readiness and marks it skipped, rather than sending something misleading.

The app ships with a Readiness tab surfacing these as a live worklist — 12 jobs missing a vendor, 3 vendors missing an email — which turns cleanup into a weekly habit instead of a one-time project that decays by month two.

Item 4 is the one that decides how good the report actually feels. "Still to do" is the section that stops phone calls, and it only has teeth when crews set Schedule as work gets booked.

Operations

Friday, unattended

mapps scheduler:create -a APP_ID \
  -s "0 20 * * 5" \
  -u "weekly-reports" \
  -n "weekly-vendor-reports" \
  -z us -r 3 -t 300

Two things to get right here. Cron runs on UTC and does not follow US daylight saving — 0 20 * * 5 is 3:00 PM Central in summer and 2:00 PM in winter. Either accept the shift or have the handler no-op outside the intended local window.

And the handler must be idempotent: key each send {vendorId}:{weekStart} in Storage and skip anything already sent. A scheduler retry that double-sends to a customer is the one failure mode that costs more trust than the report earns.

The app UI is for oversight, not operating

The cron does the sending. The Custom Object exists so somebody can see what went out and why: This week (every vendor, its report, its send state), Preview (exact HTML for any vendor and week), Readiness, History from Storage, and per-vendor Send now / Skip this week overrides.

Three columns on Vendors

Report Recipients (semicolon-separated text — deliberately separate from billing email, which is usually accounts-payable), Weekly Report (On / Paused), and Last Report Sent (date, written back by the cron so the office sees it without opening the app). No new boards.

Sequence

Build path

  1. Clean blockers 2 and 3 — dedupe vendors, collect emails. Needed before any real send.
  2. Delete the duplicate *Site Checks relation column on Jobs.
  3. Add the three Vendors columns.
  4. Scaffold the monday-code app, register the Custom Object feature, mapps code:push.
  5. Build the report function and the HTML template. Golden-file test it before anything is wired to email.
  6. Wire the email provider; store the API key with mapps code:secret.
  7. Dry run — generate all 17, send only to xander@formulaxconsulting.com.
  8. Register the cron far in the future, verify with mapps scheduler:run, then set the real schedule.
  9. Pilot two vendors for two weeks, then turn on the rest.
  10. Backfill blocker 1 through the Readiness tab as an ongoing habit.

Four calls to make

Open decisions

  • Sending domain. Sending as a Gmail address will hurt deliverability and start landing in spam at volume. A real domain with SPF and DKIM should be set up before the pilot — this is the longest-lead item on the list.
  • Email provider. Postmark has the best transactional deliverability, Resend the simplest API. Either is fine; it needs deciding early because the domain setup follows from it.
  • Which contact. Billing email is usually accounts-payable, not the person chasing status. Report Recipients exists so they can differ — but someone has to go collect those addresses.
  • Recently finished homes. Recommend including for 14 days after the Job Finish Date, so a completed home visibly lands instead of silently vanishing from the report.
